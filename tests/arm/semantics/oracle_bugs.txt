# Lines where an oracle is wrong (or is a different processor) and dismount follows the Arm ARM,
# as `[arch,...] <regex>  # <reason>`. The lines are still run: a failing line that matches is
# ORACLE_BUG instead of FAIL, a passing one is PASS. Each entry needs the evidence, so it can be
# re-checked when Unicorn is upgraded (unicorn 2.1.4 = QEMU 5.0.1) or on another host (Apple M4,
# macOS 26). `Unicorn:` entries are bugs / missing features of Unicorn, `host:` entries are
# features that the M4 doesn't implement or implements differently.
#
# --- Unicorn bugs (evidence: run_semantics.py --arch a64 --compare-oracles --file a64_ext)

# LDSMAX / LDSMIN (and the byte / halfword / acquire / release / ST forms) are swapped: the
# result is the minimum for smax and the maximum for smin. With [x4] = 5 and w1 = 0xffffffff
# (-1): ldsmax w1, w0, [x4] must leave 5 (the host does), Unicorn stores 0xffffffff; ldsmin
# must store 0xffffffff, Unicorn keeps 5. ldumax / ldumin (unsigned) agree with the host.
# Reproduced for w, x, b and h sizes with 7 value pairs (all of them differ where the signed
# and unsigned order differ). The comparison of the register results (x0 = the old value) agrees.
\b(ld|st)s(max|min)(a|l|al)?[bh]?\b  # Unicorn: LDSMAX / LDSMIN compute the opposite (min for smax, max for smin)

# --- Unicorn: missing features (QEMU 5.0.1 "max" cpu, ID_AA64ISAR/PFR registers)

# SVE2 (ID_AA64ZFR0_EL1 = 0): the unpredicated integer multiply, and every other SVE2 instruction,
# is an UNDEF (trap:undef), the host in streaming mode executes them
^mul z[0-9]+\.[bhsd], z[0-9]+\.[bhsd], z[0-9]+\.[bhsd]$  # Unicorn: no SVE2 (unpredicated MUL is SVE2)
# FEAT_BF16 and FEAT_I8MM (ID_AA64ISAR1_EL1.BF16 / I8MM = 0 on QEMU 5.0): UNDEF
[a64,unicorn] ^(bfcvt|bfcvtn2?|bfdot|bfmmla|bfmlal[bt]|smmla|ummla|usmmla|usdot|sudot)\b  # Unicorn: no FEAT_BF16 / FEAT_I8MM (the M4 has both and is the oracle)
# SME (QEMU 5.0 predates it): smstart, smstop and every streaming / ZA instruction is an UNDEF
^(smstart|smstop|zero \{za|fmopa|smopa|addha|mova z|mova za|ld1w \{za|st1b \{za|ldr za|str za|fmla za)  # Unicorn: no SME

# --- Unicorn: alignment of the acquire / release and unaligned atomic accesses.
# Unicorn faults on every unaligned exclusive, atomic (LSE) and load-acquire access (no
# FEAT_LSE2); the M4 executes the exclusives and the atomics at any address (LSE2) and faults on
# a LDAPUR that crosses a 16 byte granule. These lines use the base x6 with a misaligned
# `@state:`; all the other lines of the corpus align their atomics (states_arm.py)
^(ldxr|ldadd|swp) .*\[x6\]  # Unicorn: alignment fault for an unaligned exclusive / atomic (no FEAT_LSE2); the host executes it
^ldapur w0, \[x4, #-3\]  # Unicorn: no alignment fault for LDAPUR crossing a 16 byte granule; the host faults (SIGBUS)

# --- host (Apple M4) features
# FEAT_SM3 / FEAT_SM4: SIGILL on the M4 (hw.optional.arm has no FEAT_SM3 / FEAT_SM4); Unicorn implements them
[a64,host] ^(sm3|sm4)[a-z0-9]*\b  # host: no FEAT_SM3 / FEAT_SM4 (the M4 raises SIGILL)
# fadda and compact are not legal in the streaming mode: the host (streaming) UNDEFs them while Unicorn
# (non-streaming SVE) executes them
[a64,host] ^(fadda|compact)\b  # host: not legal in the streaming mode (SME without FA64)

# --- Instructions that neither oracle implements. Unicorn 2.1.4 (QEMU 5.0.1 "max") and the Apple M4
# both raise UNDEFINED (trap:undef), so the lifter of these cannot be compared with a processor:
# it is checked against the Arm ARM by tests/TestArm64Semantics.cpp instead. The M4 evidence is
# hw.optional.arm.FEAT_<x> = 0 (sysctl hw.optional.arm) and the SIGILL of the host runner; the
# Unicorn evidence is the missing ID_AA64 bits of QEMU 5.0 (run_semantics.py --oracle-only).
^(abs|cnt|ctz|smax|smin|umax|umin) [wx](\d+|zr), [wx]  # neither oracle has FEAT_CSSC (M4: FEAT_CSSC = 0; QEMU 5.0 predates it)
^bc\.[a-z]+ \.  # neither oracle has FEAT_HBC (M4: FEAT_HBC = 0)
^(ld64b|st64b) x  # neither oracle has FEAT_LS64 (the M4 raises SIGILL)
^(ldtadd|ldtclr|ldtset|ldtp|ldtnp|ldtxr|ldatxr|sttp|sttnp|sttxr|stltxr|swpt|cast|casat|casalt|caslt|caspt|caspat|caspalt|casplt)[a-z]* [wxqdsbh]  # neither oracle has FEAT_LSUI
^(ldapr|stlr)[bh]? [wx](\d+|zr), \[[^]]*\](!|, #)  # neither oracle has FEAT_LRCPC3 (the writeback forms)
^(ldapur|stlur) [bhsdq]\d+,  # neither oracle has FEAT_LRCPC3 (the SIMD&FP forms)

# --- Unicorn: floating point control register bits
# QEMU 5.0 keeps only the bits of FPCR it implements: the trap enables IOE..IXE (8-12), FIZ, AH
# and NEP (0-2) read as 0 after `msr fpcr`; the M4 keeps all of 0x07ff9f07 (the line passes there)
^msr fpcr, x1( ; mrs x2, fpcr)?$  # Unicorn: FPCR trap enable bits, FIZ, AH and NEP are RAZ/WI (QEMU 5.0); the M4 and dismount keep them
^stshh  # neither oracle has FEAT_PCDPHINT (the M4 raises SIGILL: hw.optional.arm has no FEAT_PCDPHINT)

# --- Unicorn (QEMU 5.0.1, EL1, MMU off) differences from the user mode of the M4 (the arbiter)
# The cache maintenance by address faults on an unmapped address on the M4 (SIGSEGV); QEMU with the MMU
# off has no fault to raise and treats dc / ic as a nop
^(dc|ic) [a-z]+, x3  # Unicorn: dc / ic by address do not fault on an unmapped address (no MMU); the M4 faults (SIGSEGV)
# FEAT_XS (dsb nXS): QEMU 5.0 predates it, the M4 runs it
^dsb [a-z]+nxs  # Unicorn: no FEAT_XS (dsb nXS is UNDEFINED)
# FPSR bits 31-28: RES0 in AArch64 (the M4 reads 0), QEMU keeps the AArch32 flags N Z C V of the FPSCR there
^msr fpsr, x1( ; mrs x2, fpsr)?$  # Unicorn: FPSR keeps the bits 31-28 (the AArch32 NZCV copies); RES0 on the M4
# XPAC: the stripped bits depend on the virtual address size (TCR_EL1.T0SZ / T1SZ and TBI). QEMU runs with TCR_EL1 = 0
# (no MMU): the field is empty and xpac returns the pointer unchanged; the M4 (47 bit addresses) strips bits 63-47
^xpac[a-z]*( x[0-9]+)?$  # Unicorn: xpac with TCR_EL1.T0SZ = 0 strips nothing; the M4 user mode has 47 bit addresses (dismount follows the M4)

# --- more instructions neither oracle implements (trap:undef on both): FEAT_LSE128 and the FEAT_LRCPC3
# pairs (the M4 raises SIGILL, QEMU 5.0 predates them); tests/TestArm64Semantics.cpp checks them. FEAT_CMPBR is
# not in the corpus at all (clang can't assemble it)
^(ldclrp|ldsetp|swpp)[a-z]* [wx]  # neither oracle has FEAT_LSE128
^(ldiapp|stilp) [wx]  # neither oracle has FEAT_LRCPC3

# --- A64 scalar floating point, Advanced SIMD and cryptography (tests/arm/semantics/corpus/a64_fp*.s, a64_neon*.s,
# a64_crypto*.s, a64_simdmem*.s; run_semantics.py --arch a64 --oracle unicorn|host)

# Instructions that neither oracle implements (trap:undef on both): the M4 lacks FEAT_FAMINMAX, FEAT_FP8, FEAT_LUT,
# FEAT_FPRCVT and FEAT_LRCPC3 (hw.optional.arm has none of them, the host runner raises SIGILL) and QEMU 5.0 predates
# them. tests/TestArm64SemanticsSimd.cpp checks the lifter against rows computed by an independent model
# (tests/arm/tools/armfp.py, which tests/arm/tools/check_armfp.py checks against the M4 for what the M4 runs)
^(famax|famin|fscale|luti2|luti4)\b  # neither oracle has FEAT_FAMINMAX / FEAT_FP8 (fscale) / FEAT_LUT
^(fcvt[nmapz][su]|[su]cvtf) ([sdh])\d+, (?!\2)[sdh]\d+$  # neither oracle has FEAT_FPRCVT (the conversions between SIMD&FP registers of different sizes)
^(ldap1|stl1) \{  # neither oracle has FEAT_LRCPC3 (the SIMD single lane acquire / release forms): trap:undef on the M4 and on QEMU 5.0

# Unicorn (QEMU 5.0.1): FCMLA by element on half precision raises extra exception flags (IOC / IDC / IXC) that the M4
# and the Arm ARM pseudocode (FPMulAdd of the pairs) don't: e.g. `fcmla v0.4h, v0.4h, v0.h[0], #0` with fpcr = 0,
# fpsr = 0 sets fpsr = 0x11 on Unicorn and 0x10 on the M4; the register results agree
[a64,unicorn] ^fcmla v\d+\.[48]h, v\d+\.[48]h, v\d+\.h\[\d\], #\d+$  # Unicorn: FCMLA by element (half) raises extra exception flags; the M4 agrees with dismount

# Unicorn: the half precision result of the fixed point conversion FCVTZS Hd, Hn, #fbits is sign extended into 32 bits
# (`fcvtzs h0, h0, #16` with h0 = 0xc000 gives 0xffff8000 on Unicorn, 0x8000 on the M4 and in the Arm ARM, which writes
# 16 bits and zeroes the rest of the register); FCVTZU is right
[a64,unicorn] ^fcvtzs h\d+, h\d+, #  # Unicorn: FCVTZS (scalar, half, fixed point) sign extends the 16 bit result into 32 bits; the M4 agrees with dismount

# FJCVTZS of a denormal flushed to zero (FPCR.FZ = 1, the input is not zero but flushed): the M4 clears Z (the
# conversion is not exact; `fjcvtzs w12, d17` with d17 = 0x000fffffffffffff, fpcr = 0x1080000 gives nzcv = 0 and IDC),
# Unicorn sets Z = 1 as for an exact zero. dismount follows the M4 (the arbiter)
[a64,unicorn] ^fjcvtzs  # Unicorn: FJCVTZS of a flushed denormal sets Z; the M4 clears it (dismount follows the M4)
# --- AArch32 integer instructions (Unicorn)
# SMLAD / SMLADX: the Arm ARM computes result = product1 + product2 + SInt(R[a]) in unbounded integers and
# sets Q only if the final sum does not fit in 32 bits. QEMU 5.0.1 adds product1 + product2 with a saturation
# check (add_setq) and then the accumulator with a second one, so Q is also set when product1 + product2 alone
# overflows and the accumulator brings the sum back: r1 = r2 = 0x80008000 gives 2^30 + 2^30 = 2^31, with
# r3 = 0x80000000 (-2^31) the sum is 0 and the Arm ARM leaves Q clear (QEMU sets it). The case is the only one
# (product1 + product2 overflows only for 0x8000 * 0x8000 twice); SMLSD subtracts without the check and agrees.
[a32,t32] ^smladx?\b  # Unicorn: SMLAD sets Q when product1 + product2 alone overflows (QEMU's two step add_setq), the Arm ARM checks the final sum

# --- AArch32 VFP / floating point (Agent F)
# The AArch32 processor oracle is Unicorn 2.1.4 (QEMU 5.0.1, CPU "max") only: the M4 cannot run AArch32. These
# entries are the instructions Unicorn does not implement or implements differently; each is backed by rows of
# tests/TestArmAArch32Semantics.cpp (tests/arm/AArch32SemanticRowsVfp.inc) computed by an independent Python
# model of the Arm ARM pseudocode (tests/arm/tools/fpmodel.py).
#
# Unicorn: no FEAT_FP16 arithmetic (MVFR1.FPHP = 0): every half precision VFP / Advanced SIMD instruction, vmov.f16,
# vins, vmovx, vldr.16 and vstr.16 are UNDEFINED (exit=trap:undef in all states; reproduce with
# run_semantics.py --arch a32 --file a32_vfp --oracle-only --grep "vadd.f16"). The conversions between half and
# single / double (vcvtb, vcvtt, vcvt.f16.f32, vcvt.f32.f16) are FEAT_FP16_CVT and run on Unicorn; FHM (vfmal,
# vfmsl) runs too.
^(?!vcvt[bt]\.f(16\.f(32|64)|(32|64)\.f16)|vcvt\.f(16\.f32|32\.f16)|vfm[as]l)\w+(\.\w+)*\.f16\b  # Unicorn: no FEAT_FP16 (half precision arithmetic is UNDEFINED)
^(vldr|vstr)\.16\b  # Unicorn: no FEAT_FP16 (vldr.16 / vstr.16 are UNDEFINED)
# Unicorn: no FEAT_BF16 (ID_ISAR6.BF16 = 0): vdot.bf16, vmmla.bf16, vfmab / vfmat and the bfloat16 conversions are UNDEFINED
^\w+(\.\w+)*\.bf16\b  # Unicorn: no FEAT_BF16 (UNDEFINED)
# QEMU 5.0.1 bug: helper_gvec_fcmlas_idx handles the vectors in segments of 16 bytes (the A64 shape) and a D
# register form (8 bytes) also writes the next D register: vcmla.f32 d0, d1, d2[0], #rot changes d1 (the upper half
# of q0) with the result of the next pair. The Arm ARM writes Dd only; reproduce with --oracle-only on that line
# (q0 upper half changes) and its fpscr flags are those of the garbage pair
^vcmla\.f32 d\d+, d\d+, d\d+\[\d\], #\d+$  # Unicorn: the D register by element form of vcmla.f32 writes 16 bytes (clobbers the next D register)
# FPSCR bits 21:20 (Stride) and 18:16 (Len) are RES0 in the Arm ARM for AArch32 ARMv8 and read as zero; QEMU keeps them
# (and has no FZ16, bit 19, without FEAT_FP16). The corpus lines with a random register mask them
^vmsr fpscr, r[01]( ; vmrs r2, fpscr)?$  # Unicorn: FPSCR keeps the RES0 Stride / Len bits (21:20, 18:16) and has no FZ16 (bit 19)

# --- Unicorn: SVE first fault loads (QEMU 5.0 sve_ldff1)
# The Arm ARM pseudocode of LDFF1 builds `result = Zeros(VL)` and writes only the elements it loaded: the
# elements from the first fault on are zero. Unicorn leaves the previous value of the destination in them
# (merging), though it sets FFR as the pseudocode does. Reproduction: ldff1sh {z11.s}, p0/z, [x4] with
# x4 = 0x1010000fffa (the window ends at 0x10100010000): lane 3 faults, Unicorn z11 lane 3 = the old 0x15151515,
# dismount 0; the same for ldff1b [x24, x2] with x24 + x2 + 13 = a 1 KiB boundary in the middle of the vector
# (QEMU's TLB treats it as a page end and "faults"); ldff1d [x4] at the window end (z25 lanes 2-7 kept).
# (run_semantics.py --arch a64 --oracle unicorn --vl 512 --file a64_sve1 --grep '^ldff1')
^ldff1[a-z]* \{  # Unicorn: LDFF1 does not zero the elements it does not load (the Arm ARM zeroes them)
